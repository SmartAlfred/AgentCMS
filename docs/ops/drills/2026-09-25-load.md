# Load test / capacity drill — 2026-09-25

Drill #3 of the WS3 production-readiness set (#24): what one AgentCMS instance
actually sustains, measured rather than asserted.  Every timestamp was printed by
`date -u +%FT%TZ` in the shell that ran the command; every derived number comes
from those timestamps and from the raw per-request samples saved as artifacts.

## Target, and the arithmetic behind it

The target is **50 requests/s sustained for 60 s** at **p95 ≤ 500 ms** and
**0 dropped requests**, with a separate measurement at **20 simultaneous
in-flight requests**.  It is derived from the product's own limits, not a wish:

```
capability_rate_limit_per_link        = 30 requests / 60 s   (app/config.py default; deploy/.env)
capability_max_live_links_per_site    = 100                  (app/config.py default)
=> one site's embedded readers may legitimately pull
   100 links x 30 reads / 60 s = 50 requests/s
```

50 rps is therefore the *ceiling the product itself permits one site to
generate* — a self-hoster running one site at its permitted maximum plus a
dashboard and a few agents.  Measured single-request latency on an idle stack
(`/blog/pre-backup-marker`, `curl` from the host) was 156 ms cold / 28 ms warm,
so 50 rps needs well under one concurrent request in flight; 20 concurrent was
chosen as an aggressive-but-plausible "20 readers at once" point and measured
separately, because a *rate* target and a *concurrency* point are different
questions.

**Trap found on the way:** the capability-authenticated read path cannot be the
capacity target.  `check_rate_limit` (`app/services/capability_tokens.py:263`)
caps every capability read at `30 / 60 s` **per link**; 40 back-to-back reads with
the drill's link returned `29x 200, 11x 429`.  A load test on that path measures
the limiter, not the server.  (Relevant alert: `agentcms_rate_limit_rejections_total`
fires at ≥ 10 in 5 min.)  Keep `/readyz` out of a capacity mix too: this stack's
readyz is legitimately `503` while the outbox backlog is non-empty, and a 503
counts as *dropped* by design.

**The target level's p95 is 14.9 ms here and was 131 ms in the ladder.**  Both are

130% CPU at `14:02:19Z`).  It did not reproduce, so it is recorded as unexplained
variance rather than attributed to the product.

### Concurrency curve (closed loop = unbounded; 60 s each)

| concurrent requests | achieved rps | p50 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: |
| 2 | 150.0 | 13 ms | 16 ms | 23 ms |
| 10 | 141.4 | 65 ms | 130 ms | 154 ms |
| 20 | 112.6 | 144 ms | 359 ms | 658 ms |
| 40 | 136.6 | 280 ms | 528 ms | 705 ms |
| 80 | 142.2 | 559 ms | 864 ms | 1134 ms |

Throughput is **flat at ~140-150 rps from 2 workers to 80**, while p50 grows
linearly: `2c 13ms, 10c 65ms, 20c 144ms, 40c 280ms, 80c 559ms` — i.e. almost
exactly `workers x 6.9 ms` (predicted 14/69/138/276/552).  That is the signature
of a **serialization point**: extra concurrency buys queueing, not throughput.

### Measured ceiling and bottleneck attribution

* **Ceiling: ~145 page renders/s**, and p95 crosses the 500 ms alert threshold
  somewhere between 20 and 40 concurrent renders.  Zero dropped requests at every
  level up to 80 concurrent — the instance degrades in *latency*, not in errors.
* **The API process is pinned to ~one core.**  `docker stats` for `ws3-drill-api-1`:
  mean **33.5%** at the target level, then **104.4 / 105.2 / 101.5%** (max 117.6%)
  at 40c-saturated, 80c@200 and 80c-saturated — flat at ~1 core no matter how much
  concurrency is thrown at it, while `ws3-drill-db-1` stayed at 21-25% (max 25.6%)
  and caddy at 2-4%.
* **That is not a cgroup limit.**  `cat /sys/fs/cgroup/cpu.max` → `max 100000`
  (no quota), `docker inspect` → `CpuQuota=0 NanoCpus=0`, the VM reports 8 CPUs,
  and **four CPU burners started inside the api container reached 400.3 / 468.5 /
  399.9 / 412.0 %** — the container may use ≥ 4 cores when asked to.
* **The serialization is inside the process.**  Exactly one uvicorn process serves
  traffic (`/proc/1/cmdline`), and the page handler is a **sync `def`**, so
  Starlette runs it in the anyio thread pool (default 40 threads) inside one
  interpreter — pure-Python template work is serialised by the GIL onto one core.
  Arithmetic: 1.05 cores / 142 rps ≈ **7.4 ms of CPU per request**, and the
  unbounded level at 40 workers reached exactly `40 / 0.281 s = 142 rps`.
* **Not the database:** `max_connections` 100 vs 11-16 backends observed, 1-2
  active, db CPU ≤ 25.6% of a core, pool `DB_POOL_SIZE=5` (+10 overflow) never
  exhausted.
* **Not the generator:** the client process used ~10-20% of one core at ≤ 200 rps,
  and the *same* generator drove **343.3 rps** (p95 339 ms) against the lighter
  `/status` route in the probe — so the tool is not the thing that stops at 145.
  Loopback only; no WAN RTT was involved.
* **Server-side cross-check:** the app's own `http_requests_total{path_template="/{site_slug}/{slug}"}`
  counted exactly what the client sent in every level (3000/3000, 8226/8226,
  8740/8740, 8600/8600, 18602/18602) and every one of them `status="200"` — the
  0.00% error rate is proven from both ends of the wire, not just the client.

### Tie-back to the alerting drill (§2 of this set)

The `HighLatencyP95` rule pages on
`histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[10m])) by (le)) > 0.5`.
At the target level the client p95 was **14.9 ms = 3.0% of the threshold** — a
20x rate increase before that page could fire.  During the saturation levels the
real ops Prometheus (`ws3-obs-prometheus-1`, which scrapes `api:8000` and
evaluates the committed rules) returned **0.875 s / 0.929 s / 0.940 s** for that
very expression at `14:08:00Z / 14:12:00Z / 14:14:00Z` — above threshold, i.e. the
rule would have been firing (10 m `for:`).  The alert is calibrated correctly
relative to the measured cliff: it fires *before* the instance is in the
queueing regime that hurts readers.

**Error budget:** 82,340 requests across all runs, **0 dropped**, so **0.00% of the
1% error budget** was consumed — no SLO erosion, and the failure mode is latency,
not errors.  (Two alerts — `OutboxBacklog`, `BackupMissed` — were already firing
on this drill stack before the run started: `/readyz` reported `queue: ok=false,
pending=2, oldest=6528s` at `13:57:31Z`.  They are ambient state of the drill
stack, not a result of the load, and were not counted as such.)

## What these numbers do NOT cover

* One route class.  `/status` (JSON, no template render) sustained 343 rps in a
  20 s probe and was **not** pushed to failure; the 145 rps ceiling is for the
  page render.  Other routes are unmeasured.
* No writes, media uploads, webhook deliveries, search, or token minting.
* One api replica, one site, warm caches, loopback (no WAN latency), TLS
  terminated on the same host; the generator shares the 8 cores with the target
  and 33 sibling containers.
* 60 s levels cannot exercise the 10-minute `for:` windows of the alert rules;
  the Prometheus p95 values quoted above are 10 m rate averages, i.e. smoothed.
* `--insecure` was used because Caddy serves its internal CA on localhost; nothing
  was weakened in the product for the drill.

## Clean-up and leftovers

The four attribution burners were SIGKILLed inside the container
(`14:1xZ`, api CPU back to 0.29% with the stack still answering `200` on
`/healthz`).  Because PID 1 in that container is `uvicorn` and not a reaper, the
four PIDs remain as **zombie entries** (`/proc/<pid>/stat` state `Z`, zero CPU and
zero memory); they disappear on the next container recreate.  The stack was
deliberately **not** restarted to clear them, so as not to fire `ServiceDown` into
the shared observability stack for cosmetic tidiness.  No volumes, test data or
running load tester were left behind.

## What this exposes (ticket)

The serialization point is real and cheap to fix in the deploy contract rather
than in the code: one `uvicorn` process with sync handlers cannot use more than
one core.  `--workers N` (or a `deploy.replicas`/`cpus` contract) would scale the
page-render ceiling by N; the drill fixes the priority and the number to beat, and
the follow-up measurement is "re-run the 40c boundless level with `--workers 4`
and expect ~4x the ceiling".  Filed as issue #47
(`ops: the api serialises page renders onto one core`) so it does not become a
repeated incident.
